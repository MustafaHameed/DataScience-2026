\section{The problem}

Two campus sites need to exchange traffic and the only path between them is the
internet, which is shared with everyone and trusted by nobody. Anything sent in
clear can be read; anything read can be altered; anything altered can be replayed.

A \term{virtual private network} makes that shared path behave like a private
one. \term{IPsec} is the standard suite of protocols that does it at the network
layer --- which is the useful part, because it means applications need no
changes and know nothing about it.

\begin{definitionbox}[The four services IPsec provides]
\begin{tight}
  \item \textbf{Confidentiality} --- encryption, so the payload cannot be read.
        Normally AES.
  \item \textbf{Integrity} --- a keyed hash, so alteration is detectable.
        Normally SHA-2.
  \item \textbf{Authentication} --- proof that the peer is who it claims to be.
        A pre-shared key or a digital certificate.
  \item \textbf{Anti-replay} --- sequence numbers, so a captured packet cannot be
        re-sent later to useful effect.
\end{tight}
Underpinning all four is \textbf{key management}: Diffie--Hellman, which lets two
peers agree a shared secret over a channel an eavesdropper is watching.
\end{definitionbox}

\begin{conceptbox}[Traffic is only protected inside the tunnel]
In the site-to-site diagram, traffic between the host and its own gateway is in
clear. IPsec protects the internet crossing, not the LAN at either end. That is
usually the right trade --- but it means a VPN is not an answer to a threat
already inside the building.
\end{conceptbox}

\section{The protocols}

Three names, and the exam expects you to know which does what.

\begin{longtable}{@{}L{2.4cm}L{2.7cm}L{4.5cm}L{5.3cm}@{}}
\toprule
\rowcolor{primary!15}
\textbf{Protocol} & \textbf{Identifier} & \textbf{Provides} & \textbf{Notes} \\
\midrule
\endhead
IKE & UDP 500, and UDP 4500 with NAT-T &
Peer authentication, key exchange, negotiation of everything else &
The control plane. Nothing is encrypted until IKE has finished \\
\rowcolor{lightbg}
ESP & IP protocol 50 &
Confidentiality, integrity, authentication, anti-replay &
\textbf{What is actually used.} The only one of the three that encrypts \\
AH & IP protocol 51 &
Integrity, authentication, anti-replay --- \textbf{no encryption} &
Effectively obsolete. Breaks through NAT; see below \\
\bottomrule
\end{longtable}

\begin{alertbox}[Two facts that are asked directly]
\textbf{ESP encrypts; AH does not.} If a question asks which protocol provides
confidentiality, the answer is ESP, every time.

\textbf{ESP and AH are not TCP or UDP.} They are IP protocols in their own right,
numbered 50 and 51, sitting at the same layer as TCP~(6) and UDP~(17). This is
why a firewall rule that permits ``UDP 500'' alone will let the tunnel negotiate
and then carry no data --- a memorable and very common real fault.
\end{alertbox}

\subsection{IKE, in two phases}

\begin{tight}
  \item \textbf{Phase 1} builds a secure, authenticated channel between the two
        peers --- the ISAKMP or IKE security association. The peers prove their
        identity (pre-shared key or certificate) and run Diffie--Hellman.
  \item \textbf{Phase 2} uses that channel to negotiate the security
        associations that will actually protect user traffic, including which
        traffic is to be protected at all.
\end{tight}

IKEv2, the current version, does the same work in fewer exchanges, and adds
built-in NAT traversal and liveness checking. New deployments use it.

\begin{definitionbox}[Security association]
A one-directional agreement covering the algorithms, keys and lifetimes for one
flow. Because it is one-directional, a working tunnel has \emph{two} --- one in
each direction. Asymmetric failures, where traffic passes one way only, are
usually a phase 2 mismatch.
\end{definitionbox}

\begin{examnote}[If the question does not say otherwise, it is tunnel mode]
Tunnel mode is the default for the VPNs this topic names. The single sentence to
remember: \textbf{tunnel mode encrypts the original IP header and adds a new one;
transport mode does not.} Every other difference in the table follows from that.
\end{examnote}

\section{IPsec and NAT}

\begin{alertbox}[Why AH is dead]
AH authenticates the \emph{entire} packet, including the source and destination
addresses in the IP header. NAT's whole job is to rewrite those addresses. So a
NAT device on the path invalidates AH's integrity check by definition, and the
far end discards the packet.

There is no configuration that fixes this; the two mechanisms are logically
incompatible. Since almost every internet path involves NAT somewhere, AH has
been left behind, and ESP --- which does not protect the outer header --- is what
everyone uses.
\end{alertbox}

ESP has a milder version of the same problem: PAT needs port numbers to
multiplex, and ESP is not a port-based protocol. \term{NAT traversal} solves it by
detecting NAT on the path during IKE and wrapping ESP inside UDP port~4500, which
PAT can then handle normally. It is automatic in IKEv2.

\begin{conceptbox}[GRE over IPsec, in one paragraph]
IPsec tunnel mode carries unicast IP and nothing else --- no multicast, and
therefore no routing protocols. A site-to-site VPN that needs OSPF between the
sites wraps the traffic in a GRE tunnel first, which \emph{can} carry multicast,
and then protects the GRE with IPsec.

You will meet the phrase ``GRE over IPsec''. For this exam, know why it exists:
GRE brings the ability to run a routing protocol, IPsec brings the security, and
neither does both.
\end{conceptbox}

\section{When things do not work}

Not examined as a configuration task, but these four explain most real failures
and make the mechanics concrete.

\begin{tight}
  \item \textbf{Phase 1 never completes.} Mismatched pre-shared key, mismatched
        IKE proposal, or UDP~500 blocked. Nothing at all passes.
  \item \textbf{Phase 1 completes, phase 2 does not.} Mismatched transform set,
        or the two ends disagree about which traffic should be protected. The
        peers can talk; user traffic cannot.
  \item \textbf{Tunnel establishes, large packets fail.} The extra headers push
        packets past the path MTU. Small pings and SSH work, file transfers and
        web pages hang. A classic, and a good reminder that ``it pings'' is not
        ``it works''.
  \item \textbf{Everything negotiates and no data flows.} A firewall permitting
        UDP~500 but not IP protocol~50.
\end{tight}

\begin{pitfall}
\begin{tight}
  \item \textbf{Saying AH encrypts.} It does not. Only ESP does.
  \item \textbf{Calling ESP and AH ``TCP'' or ``UDP''.} They are IP protocols 50
        and 51.
  \item \textbf{Mixing up the modes.} Tunnel mode adds a new IP header; transport
        mode keeps the original.
  \item \textbf{Assuming a VPN protects the whole path.} It protects the tunnel.
  \item \textbf{Expecting a routing protocol to run over plain IPsec.} It cannot
        --- multicast needs GRE.
  \item \textbf{Treating a successful ping as a working tunnel.} Test with
        something large enough to expose an MTU problem.
\end{tight}
\end{pitfall}

\begin{breakfix}[The tunnel is up and shows both peers established. No user traffic crosses it.]
A site-to-site VPN between \cmd{R1} and \cmd{R2}. Both routers report an
established IKE session with the other. Users at either site cannot reach the
other site at all.

\begin{verify}{R1}{show crypto isakmp sa}
IPv4 Crypto ISAKMP SA
dst             src             state          conn-id status
198.51.100.9    203.0.113.2     QM_IDLE           1004 ACTIVE
\end{verify}

\begin{verify}{R1}{show crypto ipsec sa | include pkts|local ident|remote ident}
   local  ident (addr/mask/prot/port): (192.168.10.0/255.255.255.0/0/0)
   remote ident (addr/mask/prot/port): (192.168.20.0/255.255.255.0/0/0)
    #pkts encaps: 0, #pkts encrypt: 0, #pkts digest: 0
    #pkts decaps: 0, #pkts decrypt: 0, #pkts verify: 0
\end{verify}

\textbf{Diagnosis.} Read the two outputs as a pair, because together they locate
the fault precisely.

\cmd{QM\_IDLE} and \cmd{ACTIVE} mean \textbf{phase 1 succeeded}: the peers found
each other, agreed on IKE parameters and authenticated. So the pre-shared key is
right, UDP~500 is reaching both ends, and the peer addresses are correct. All of
that is now ruled out.

But every counter is zero --- in \emph{both} directions. Nothing has been
encrypted and nothing decrypted. Traffic is not being selected for the tunnel, or
is being selected and then dropped before it is sent.

The identities are the place to look. \cmd{R1} intends to protect
\cmd{192.168.10.0/24} to \cmd{192.168.20.0/24}. If \cmd{R2}'s definition is not
the exact mirror --- a different mask, a wider or narrower range --- phase 2
cannot agree on what the tunnel is for, and no traffic qualifies.

\textbf{The class of fault, which is the point here.} Phase 1 up with phase 2
idle is always a \emph{policy} disagreement rather than a connectivity or
credential one: the crypto ACL, the transform set, or the mode. Knowing which
half of IKE succeeded halves the search before you have looked at anything.

\textbf{The other candidate}, if the identities do match, is a firewall permitting
UDP~500 --- which is why phase 1 worked --- while dropping IP protocol~50.
Symptoms are identical; the discriminator is whether \cmd{\#pkts encaps} is zero
(traffic never selected) or climbing while \cmd{\#pkts decaps} stays at zero
(sent, never arriving).
\end{breakfix}

\begin{chaptersummary}
\begin{tight}
  \item IPsec provides confidentiality, integrity, authentication and
        anti-replay, with Diffie--Hellman for key agreement.
  \item Site-to-site joins two gateways and is invisible to hosts; remote access
        runs from a user's device to a gateway and authenticates the user.
  \item IKE (UDP 500, or 4500 with NAT-T) negotiates. ESP (IP protocol 50)
        protects data and \textbf{encrypts}. AH (IP protocol 51) authenticates
        but does \textbf{not} encrypt.
  \item Phase 1 builds the secure channel between peers; phase 2 builds the
        security associations that protect user traffic. SAs are
        one-directional, so a working tunnel has two.
  \item Tunnel mode encrypts the whole original packet and adds a new IP header
        --- the normal case. Transport mode keeps the original header.
  \item AH is incompatible with NAT because it authenticates the header NAT
        rewrites. ESP with NAT-T (UDP 4500) is the working combination.
  \item Plain IPsec carries no multicast, so a VPN needing a routing protocol
        uses GRE over IPsec.
\end{tight}
\end{chaptersummary}
